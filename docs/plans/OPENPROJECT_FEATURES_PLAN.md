# LRS Boards — Project Suite: Architecture & Implementation Plan

**Audience:** Claude Sonnet 5 (implementing agent). Read this document top to bottom before writing any code.
**Goal:** Bring five OpenProject-inspired features into LRS Boards (this repo), reimplemented natively in our stack, plus a strong member-management surface:

1. **Wiki** — per-project hierarchical markdown pages with revision history
2. **Documents** — per-project file library with folders and descriptions
3. **Media** — per-project gallery of all images/files (documents + card attachments)
4. **Gantt charts** — per-project timeline of cards with dependencies, saved named views
5. **Team Planner** — per-project resource calendar (members × time) of assigned cards
6. **Members board** — one admin overview of who has access to which projects and boards, with per-project member management

Future milestones are also specified here but are **not** part of the current build: §14 PenPot integration (Milestone 2), §15 personal time tracking (Milestone 3), and §16 Milestone 4 candidates (global search, My Work dashboard, client share links, estimates, team hours report, iCal feed, audit log). Do not implement them until explicitly asked; they exist so Phases 0–6 stay compatible with them.

**Do not port code from OpenProject** (`H:\openproject`). It is Rails + Angular; we are Sails.js 1.5 + Waterline + Postgres (server) and React 18 + Redux + redux-orm + redux-saga (client). OpenProject is only the semantic reference for what these features do. This document already extracts what matters.

## 1. System context — what this codebase is

LRS Boards is a 4ga Boards fork (Planka lineage). Monorepo:

- `server/` — Sails.js 1.5, Waterline ORM, Postgres, knex migrations in `server/db/migrations/`, socket broadcasts via `sails.sockets`.
- `client/` — React 18, CRA-style webpack, Redux + redux-orm + redux-saga, SCSS modules, react-router 7, i18next.

### 1.1 Existing domain model

```
User
Project ──< Board ──< List ──< Card ──< Task, Attachment, Action(comments/activity)
ProjectManager (user ↔ project, manager rights)
BoardMembership (user ↔ board, role: editor | viewer, canComment)
CardMembership, TaskMembership, CardLabel, Label, CardLink (references | blockedBy)
UserProject (per-user project UI prefs, e.g. isCollapsed)
Core (singleton instance settings), UserPrefs, Notification, Session
```

Key facts you will build on:

- **There is no project-level membership today.** Access to a project's content is implied by having a membership on ≥1 of its boards; management rights come from `ProjectManager` or `user.isAdmin`. This plan introduces `ProjectMembership` (§3.1).
- `Card` has `dueDate` but **no `startDate`** — Gantt/Team Planner need one (§8.1).
- `Attachment` is **card-bound** (`cardId` required) and stores its own file (`dirname`, `filename`, `image` json) with `customToJSON()` producing `url`/`coverUrl`. Documents replicate this file-record pattern rather than generalizing Attachment (§2, D4).
- `CardLink.Types = { REFERENCES: 'references', BLOCKED_BY: 'blockedBy' }` — Gantt dependency arrows come from `blockedBy` links.
- IDs are bigints generated by the Postgres `next_id()` function (see any migration).

### 1.2 The reference vertical slice: card-links

`card-links` is the most recent, cleanest end-to-end entity. **When this plan says "mirror card-links", copy its structure exactly.** The full slice:

**Server**

- `server/config/routes.js` — explicit REST route entries

**Client**
- `client/src/api/card-links.js` + registered in `client/src/api/index.js`
- `client/src/constants/ActionTypes.js` — `X_CREATE`, `X_CREATE__SUCCESS`, `X_CREATE__FAILURE`, `X_CREATE_HANDLE` (the `_HANDLE` variant is for socket-received events)

**Every new entity in this plan (WikiPage, Document, ProjectMembership, ChartView) gets this exact treatment.** When board-scoped doesn't apply, broadcast to a project room instead (§3.4).

### 1.3 Client rendering architecture

## 2. Cross-cutting architecture decisions

These are decided. Do not re-litigate them during implementation.

**D1 — Reimplement, don't port.** OpenProject code is never copied. Feature semantics documented here are the spec.

**D2 — `ProjectMembership` becomes a first-class entity.** New table + model + full slice. `ProjectManager` stays as-is (it's woven through the whole app); the members UI presents managers and members as one unified list, backed by the two tables. Rationale: unifying the tables is a high-risk refactor with no user-visible payoff; the UI-level merge gets the same UX. See §3.1.

**D3 — Project features are project-scoped, not board-scoped.** Wiki, Documents, Media, Gantt, Team Planner each live at the project level (one instance per project, per the product requirement). Access requires project membership (or manager/admin). Socket updates broadcast to a new `project:<id>` room (§3.4).

**D4 — Documents own their files; Attachment stays card-only.** `Document` copies Attachment's proven file-record pattern (`dirname`/`filename`/`image` json + `customToJSON` URL synthesis + the `process-uploaded-file` helper approach) instead of making `Attachment.cardId` nullable/polymorphic. Rationale: zero regression risk to the card attachment path, and Media (§7) is a read-only aggregation so no shared table is needed.

**D5 — Media is a view, not a store.** No new table. One aggregate endpoint that returns the project's documents + card attachments, rendered as gallery/list. Uploading "to media" creates a Document.

**D6 — Gantt and Team Planner render cards, not a new entity.** They are alternative views over `Card` (+ `CardMembership`, `CardLink`), exactly as OpenProject's Gantt/Team Planner are views over work packages. The only new persistence is `Card.startDate` and saved view configs (`ChartView`, §8.2). Editing in these views issues ordinary card updates, so the kanban board, list view, and these views stay live-consistent through existing socket events.

**D7 — Timeline components are built in-house.** No new chart/calendar dependency. Both Gantt and Team Planner share one custom timeline engine (§8.4) built with divs/CSS grid + `react-window` — this repo's dependency set is curated, and drag interactions must match existing UX. FullCalendar/dhtmlx are explicitly rejected.

**D8 — Navigation: a project hub with tabs.** A new horizontal `ProjectNav` tab bar under the header whenever a project context is active. The left sidebar keeps its current role (projects/boards tree). See §10 for the full UI spec.

**D9 — Ship in phases; each phase is independently releasable** (§12). Never break existing kanban flows; all new tables are additive; the only ALTER on an existing table is adding nullable `card.start_date`.

## 3. Foundation phase (Phase 0) — ProjectMembership, project rooms, project hub

Everything else depends on this phase.

### 3.1 `ProjectMembership` — data model

Migration `create_project_membership`:

```js
// table: project_membership
table.bigInteger('id').primary().defaultTo(knex.raw('next_id()'));
table.bigInteger('project_id').notNullable();
table.bigInteger('user_id').notNullable();
table.text('role').notNullable();            // 'member' (managers stay in project_manager)
table.boolean('can_edit_wiki').defaultTo(true);
table.boolean('can_manage_documents').defaultTo(true);
table.bigInteger('created_by_id');
table.timestamp('created_at', true);
table.timestamp('updated_at', true);
table.unique(['project_id', 'user_id']);
table.index('user_id');
```

**Backfill in the same migration:** insert a `project_membership` row (role `member`) for every distinct `(project_id, user_id)` derivable from existing `board_membership` joined through `board` — existing users keep exactly the access they have. Do not backfill rows for users who are already project managers.

Server model `server/api/models/ProjectMembership.js` with `Roles = { MEMBER: 'member' }`, mirroring `BoardMembership.js` conventions (`tableName`, `columnName`s).

**Semantics:**
- Project membership grants: project visible in sidebar; access to Wiki/Documents/Media/Gantt/Team Planner; **no board access by itself** — board access remains exclusively `BoardMembership`, which admins/managers toggle per board as today.
- Creating a `BoardMembership` for a user who lacks a `ProjectMembership` on that board's project **auto-creates one** (helper-level, so imports and existing flows stay consistent). Deleting a project membership cascades: delete that user's `BoardMemberships` on the project's boards, `CardMemberships`/`TaskMemberships` beneath them (follow the existing cascade patterns in `board-memberships/delete-one` helpers).
- `ProjectManager` implies everything a member has, plus manage rights. `user.isAdmin` implies everything everywhere.

**Routes:**

```
POST   /api/projects/:projectId/memberships    → project-memberships/create   (admin or project manager)
PATCH  /api/project-memberships/:id            → project-memberships/update   (toggle canEditWiki etc.)
DELETE /api/project-memberships/:id            → project-memberships/delete
```

Full slice per §1.2 (`project-memberships` controllers/helpers, client `models/ProjectMembership.js`, sagas, etc.). Socket events `projectMembershipCreate|Update|Delete` broadcast to the project room and to `user:<userId>` (so the added user's sidebar gains the project live — mirror how board memberships notify users today; find the existing pattern in `board-memberships` helpers and copy it).

### 3.2 Permission helper

Add `server/api/helpers/projects/get-membership-context.js`: given `(projectId, currentUser)` returns `{ isAdmin, isManager, isMember, membership }` in one place. **Every new controller in this plan calls this helper** instead of re-deriving permissions. Read checks: `isAdmin || isManager || isMember`. Manage checks: `isAdmin || isManager`.

### 3.3 Data loading

The current bootstrapping loads projects/boards via `user-projects` and `projects` endpoints. Extend `projects/index` and `projects/show` controller responses to include `projectMemberships` (and keep including `projectManagers`), so the client ORM can hydrate `ProjectMembership` alongside. Follow how `boards/show` includes its `memberships` in the response payload — search `server/api/controllers/projects/show.js` for the included-records pattern and extend it.

### 3.4 Project socket room

Boards use `board:<id>` rooms (clients subscribe when entering a board). Add a `project:<id>` room: find where the client subscribes to board rooms (`server/api/controllers/boards/show.js` calls something like `sails.sockets.join`; trace it) and implement the same for `projects/show` + wherever project-scoped feature data is fetched. All Wiki/Document/ChartView events broadcast there. Card updates continue to broadcast to board rooms — Gantt/Team Planner clients must therefore also be subscribed to the project's boards' rooms **or** (simpler, do this) the Gantt/Planner data endpoint returns cards and the client relies on the fact that a user viewing Gantt has the project's board data loaded via the same fetch (§8.3); card socket events for boards the user is a member of already flow today.

### 3.5 Project hub routing shell

- `Paths.js` additions:

```js
const PROJECT_GANTT       = `${Config.BASE_PATH}/projects/:id/gantt`;
const PROJECT_TEAM        = `${Config.BASE_PATH}/projects/:id/team-planner`;
const PROJECT_WIKI        = `${Config.BASE_PATH}/projects/:id/wiki`;
const PROJECT_WIKI_PAGE   = `${Config.BASE_PATH}/projects/:id/wiki/:slug`;
const PROJECT_DOCUMENTS   = `${Config.BASE_PATH}/projects/:id/documents`;
const PROJECT_MEDIA       = `${Config.BASE_PATH}/projects/:id/media`;
const PROJECT_MEMBERS     = `${Config.BASE_PATH}/projects/:id/members`;
const SETTINGS_MEMBERS    = `${Config.BASE_PATH}/settings/members`;
```

- Register routes wherever `Paths.PROJECTS` is currently matched (trace `client/src/sagas/core/services/router.js` and the root route table — likely `Root.jsx`/router service — and add the new paths the same way `SETTINGS_*` paths are matched).
- `Static.jsx`: add branches before the `board === undefined` fallback: when `path` is one of the new project paths, render the corresponding container inside `SidebarContainer` (same wrapper as `BoardsContainer`).
- New `ProjectNav` component (§10.2) rendered by each project-scoped page (Boards grid included) so the tab bar is persistent across the hub.

## 4. Members board (Phase 1)

Two surfaces sharing components: a **global admin overview** and a **per-project members page**.

### 4.1 Global overview — `/settings/members` (admin only)

Placement: new entry in the settings sidebar under "Instance settings" (next to Users), icon `IconType.Users`. `Static.jsx` routes it like other `SETTINGS_*` paths; extend `Settings.jsx` switchboard and the settings `Sidebar` block.

**Endpoint:** `GET /api/members-overview` → admin-gated controller `server/api/controllers/users/members-overview.js` (or new `members/` controller dir) returning, in one round trip:

```js
{
  items: [{
    userId, name, username, email, avatarUrl, isAdmin, lastLogin,
    projects: [{
      projectId, projectName,
      role: 'manager' | 'member',            // from project_manager / project_membership
      projectMembershipId, projectManagerId, // whichever applies
      boards: [{ boardId, boardName, boardMembershipId|null, role: 'editor'|'viewer'|null }]
    }]
  }]
}
```

Build it server-side with a handful of `find` queries + in-memory joins (follow the parallel-query style used in `boards/show`); do not N+1 per user.

**UI — `MembersSettings` component (`client/src/components/Settings/MembersSettings/`):**

- Layout mirrors `UsersSettings` (header, search input, `Utils/Table`).
- **Master–detail:** left = user table (avatar, name, admin badge, "N projects / M boards" summary cells, last activity); selecting a row opens the right detail panel (or expands inline on narrow widths).
- **Detail panel** for the selected user: one section per project — project name, role chip (`Manager` amber / `Member` neutral, using existing label-color variables), then a board checklist: each of the project's boards with a toggle (uses `Utils/Checkbox`) and, when on, an editor/viewer dropdown (`Utils/Dropdown`). Toggling creates/deletes `BoardMembership`; the dropdown patches its `role` — all through the **existing** board-membership entry actions.
- Top-level actions: "Add to project…" popup (project picker → creates ProjectMembership; optional "as manager" switch → creates ProjectManager instead), "Remove from project" (confirm via existing `DeleteStep` pattern; explains the cascade).
- **Matrix mode toggle** (icon button in the header): grid of users × projects; each cell shows `—` / `M` / `✓ n/k` (member with n of k boards); clicking a cell opens a popup with that user+project's board toggles. This is the "one good overview" — implement it as a second render mode of the same data, not a separate page.
- Everything updates optimistically through the normal saga flow; socket `_HANDLE` actions keep multiple admin sessions consistent.

### 4.2 Per-project members — `/projects/:id/members`

Visible to project managers/admins via a `Members` tab in `ProjectNav` (hidden for plain members). Component `client/src/components/Project/ProjectMembers/`:

- Same table primitives, scoped to one project: rows = users with a `ProjectMembership` or `ProjectManager` on this project.
- Columns: user (avatar+name), role (Member/Manager — managers editable by admin only), per-feature flags (`canEditWiki`, `canManageDocuments` as checkboxes), then **one column per board** with a membership toggle + editor/viewer dropdown (horizontally scrollable board columns; sticky user column).
- "Add member" button (manager+) → user picker popup (reuse `UserAddStep`-style search over `/api/users` the way board membership adding works today).
- Remove member → confirm step, cascades per §3.1.

## 5. Wiki (Phase 2)

One wiki per project. OpenProject semantics kept: hierarchical pages, slugs unique per project, revision history, a default landing page.

### 5.1 Data model

Migration `create_wiki_pages`:

```js
// table: wiki_page
id (next_id PK), project_id NOT NULL (index), parent_id NULL,
title text NOT NULL, slug text NOT NULL, content text NOT NULL DEFAULT '',
position float NOT NULL,                    // sibling ordering, same scheme as List/Card position
created_by_id, updated_by_id, created_at, updated_at
unique(['project_id', 'slug'])

// table: wiki_page_revision
id (PK), wiki_page_id NOT NULL (index), title text, content text,
created_by_id, created_at
```

- Slug: lodash `kebabCase(title)`, uniquified with `-2`, `-3`… suffix within the project (server helper; recompute on rename, and write a revision on rename too).
- On every content/title update, insert a `wiki_page_revision` row of the **previous** state (write-behind history, like OpenProject journals). Cap: keep the latest 100 revisions per page (delete older in the update helper).
- Deleting a page re-parents its children to the deleted page's parent (OpenProject `dependent: :nullify` behavior — never cascade-delete a subtree without the user asking; the delete confirm popup offers "delete subtree" as an explicit checkbox, which then deletes descendants recursively).

### 5.2 API

```
GET    /api/projects/:projectId/wiki-pages          → index (tree: all pages, no content field)
POST   /api/projects/:projectId/wiki-pages          → create { title, parentId?, content? }
GET    /api/wiki-pages/:id                          → show (full content + latest 20 revisions' metadata)
PATCH  /api/wiki-pages/:id                          → update { title?, content?, parentId?, position? }
DELETE /api/wiki-pages/:id                          → delete { withChildren? }
GET    /api/wiki-pages/:id/revisions/:revisionId    → revision content (for diff/restore)
POST   /api/wiki-pages/:id/revisions/:revisionId/restore → restore
```

Permissions: read = project member+; write = member with `canEditWiki` (default true) or manager/admin. Socket events `wikiPageCreate|Update|Delete` → `project:<id>` room (index payloads exclude `content` to keep broadcasts small; the open editor refetches on external update and shows a non-blocking "page was updated by X" banner rather than clobbering local edits).

### 5.3 UI — `/projects/:id/wiki[/:slug]`

`client/src/components/Project/Wiki/`:

- **Two-pane layout** inside the hub: left, a page tree (280px, collapsible — reuse the sidebar visual language: same item/hover/active styles as `Sidebar.module.scss`); right, the page.
- Tree: expand/collapse carets (`IconType.TriangleDown` like project collapse), drag to reorder/re-parent with `react-beautiful-dnd` (nested droppables per parent, same pattern as board reordering), "+" at each level and a root "New page" button.
- Page view: title (inline-editable heading, `TextArea`-based like card names), rendered markdown via `Utils/Markdown`, metadata line ("Updated by {user} {relative time} · History"), Edit button (pencil icon) for users with write rights.
- Edit mode: full-width `@uiw/react-md-editor` (same configuration as the card description editor — find it in `CardModal` and reuse its wrapper/props), Save/Cancel bar pinned at the bottom, `Ctrl+Enter` saves (match card description behavior). Warn on navigation with unsaved changes.
- History: right-side popup/panel listing revisions (author avatar, timestamp); selecting one shows read-only content with a "Restore this version" button.
- Default page: opening `/wiki` with zero pages shows an empty state ("Create the first page" CTA); with pages, redirects to the first root page by position.
- Wiki-links: extend the existing Markdown renderer minimally — `[[Page Title]]` resolves against the loaded page tree to a wiki link (unresolved renders with a subtle "missing" style and creates the page on click for writers). Implementation: a small remark/rehype visitor in `Utils/Markdown`'s plugin chain (it already uses `remark-github`/`rehype-*` plugins — add alongside, gated by a prop so card descriptions are unaffected).

## 6. Documents (Phase 3)

Per-project file library. OpenProject's Documents module = titled, described, categorized files at project level; ours: folders + title + description, one file per document (multi-file needs = multiple documents; keep V1 simple).

### 6.1 Data model

Migration `create_documents`:

```js
// table: document
id (PK), project_id NOT NULL (index),
folder text NULL,                 // flat single-level folders, derived list — no folder table
name text NOT NULL,               // display title
description text NULL,
dirname text NOT NULL, filename text NOT NULL, image json NULL,  // same trio as attachment
created_by_id, updated_by_id, created_at, updated_at
index(['project_id', 'folder'])
```

Model `Document.js` copies `Attachment.js` including a `customToJSON()` that emits `url` and `coverUrl` (new download namespace below). File processing: reuse the logic in `server/api/helpers/attachments/process-uploaded-file.js` — extract the shared parts into `server/api/helpers/utils/` if trivially extractable, otherwise copy into `helpers/documents/process-uploaded-file.js` (do not destabilize the attachment path).

### 6.2 API

```
GET    /api/projects/:projectId/documents        → index
POST   /api/projects/:projectId/documents        → create (multipart upload; skipper, same as attachments/create)
PATCH  /api/documents/:id                        → update { name?, description?, folder? }
DELETE /api/documents/:id                        → delete
GET    /documents/:id/download/:filename         → download        (skipAssets: false, mirror attachment routes)
GET    /documents/:id/download/thumbnails/cover-256.:extension → thumbnail
```

Download authorization must check project membership (mirror how `attachments/download` authorizes via board membership — read it first). Permissions: read = member+; create/update = member with `canManageDocuments` or manager; delete = uploader, manager, or admin. Sockets `documentCreate|Update|Delete` → project room.

### 6.3 UI — `/projects/:id/documents`

`client/src/components/Project/Documents/`:

- Header row: folder breadcrumb/filter chips ("All" + one chip per folder + "＋ New folder" which is just naming a folder on upload/move), search input (client-side filter), view toggle (list ⇄ grid), Upload button.
- **List view** (default): `Utils/Table` — icon/thumbnail, name (+description as secondary line), folder, size?/type (derive type client-side from filename extension; size only if trivially available from the upload metadata — otherwise omit, don't stat files per request), uploaded by (avatar), date, actions cell (rename/edit description via popup, move to folder, download, delete with confirm).
- **Grid view**: cards with `coverUrl` thumbnails (images) or a large type icon; reuses the same actions popup.
- Upload: `Utils/FilePicker` + `react-dropzone` full-page drop target (same as CardModal attachments); progress via existing `ProgressBar`.
- Empty state: illustration-free, headline + "Upload your first document" CTA (match the wiki empty-state styling).

## 7. Media (Phase 4 — small)

## 8. Gantt charts (Phase 5)

A per-project timeline of cards. This is the biggest build; it shares its engine with Team Planner.

### 8.1 `Card.startDate`

Migration `add_start_date_to_card`: `table.timestamp('start_date', true);` (nullable). `client/src/components/Project/Timeline/` — pure presentational engine used by both features:

## 14. Milestone 2 (future, after Phases 0–6): PenPot integration

Not part of the current implementation phases — **do not build any of this until the user green-lights Milestone 2.** Documented here so architectural choices in Phases 0–6 stay compatible with it, and so the eventual implementer has the decided approach.

PenPot (`H:\penpot`) is an open-source design tool: Clojure/JVM backend, ClojureScript frontend, a `render-wasm` engine, a Node exporter service, Postgres + Redis. Verified integration seams in its codebase: `backend/src/app/rpc/commands/` contains `access_token.clj` (personal/service API tokens), `files_share.clj` + `viewer.clj` (view-only share links with an embeddable viewer), `files_thumbnails.clj` (thumbnail endpoints), `webhooks.clj` (change notifications), plus a first-class `plugins/` workspace (TypeScript plugins that run inside PenPot).

**Decisions (locked):**

- **M2-D1 — Sibling service, not absorbed.** PenPot runs as its own containers next to our stack. Its stack shares nothing with Sails/React; none of its features get reimplemented in this app.
- **M2-D2 — Pin, don't fork.** Deploy official `penpotapp/*` Docker images pinned to release tags; upgrades = tag bumps. Customization order: env/config first, PenPot plugin API second, our own integration layer third. Forking PenPot core is rejected.
- **M2-D3 — Static by default, live on demand.** Our app never loads PenPot assets passively. Surfaces show thumbnails cached in our storage; the view-only share-link viewer loads in an iframe only after an explicit user click; the full editor is never embedded — "Open in PenPot" opens a new tab.

**Architecture:**

- **Deployment:** add `penpot-frontend`, `penpot-backend`, `penpot-exporter`, and Redis to `docker-compose.yml`; separate `penpot` database on the existing Postgres instance; reverse-proxy under a subdomain or path.
- **Identity:** both apps are OIDC clients — a shared IdP gives SSO. Server-to-server: one PenPot service access token held in Sails config (env var), used for RPC calls (`/api/rpc/command/...`) to list files, fetch thumbnails, and manage share links.
- **Data model:** new `design_file` table — `id, project_id (index), penpot_file_id, name, thumbnail_dirname/filename (cached copy in our attachment-style storage), share_link_url, created_by_id/updated_by_id, timestamps`. Full vertical slice per §13. Permissions: read = project member+, link/unlink = member, delete-link = manager (never deletes the PenPot file).
- **Thumbnail cache + invalidation:** our server fetches/export thumbnails via PenPot's thumbnail/exporter endpoints and stores them locally; a PenPot **webhook** endpoint on our server (`POST /api/webhooks/penpot`, token-authenticated) marks affected `design_file` rows stale and refreshes their thumbnails (background, debounced). No PenPot call ever happens in the request path of a page load.
- **UI:** new `Design` tab in `ProjectNav` (icon: brush; visible to project members+): grid of linked files with cached thumbnails, "Edited by X · when" metadata, per-card `Open in PenPot` (new tab) and `Live preview` (click-to-load share-link viewer iframe) actions; "New in PenPot" creates a file via RPC in the project's mapped PenPot project and links it. Cards may reference a `design_file` (small indicator like the attachment icon, linking to the Design tab). Wiki embed syntax `[[penpot:<design-file-name-or-id>]]` renders the cached thumbnail card linking out (same Markdown-plugin mechanism as §5.3 wiki-links). Media (§7) includes design thumbnails in its aggregation from the cache.
- **Cost note:** client performance is unaffected by design; the real cost is server RAM (~1–2 GB for JVM + exporter + Redis) — a hosting decision to confirm before starting M2.

**Sequencing:** requires Phase 0 (ProjectMembership, ProjectNav, project rooms); pairs naturally after Wiki (§5) and Media (§7) so the embed and aggregation hooks exist.

## 15. Milestone 3 (future, after Phases 0–6): Personal time tracking (Jibble replacement)

Not part of the current implementation phases — **do not build until the user green-lights Milestone 3.** Independent of Milestone 2 (PenPot); can ship before or after it.

**Context:** the team currently uses Jibble for exactly one workflow: in a week-view calendar they drag-select time slots, attach descriptions, and save; later they export a date range to populate an invoice sent to LRS for payment. This milestone replaces that workflow in-app, matching Jibble's ease of use, plus a one-time migration path for existing Jibble data.

**Decisions (locked):**

- **M3-D1 — User-scoped, not project-scoped.** One timesheet per user account. Visible and editable by its **owner and by admins**: admins can view every member's timesheet and create/edit/delete entries on any member's behalf (correcting or backfilling time before invoicing). Project managers get no access — this is admin-level, not project-level. The timesheet does *not* live in `ProjectNav`; it is an account-level page like Notifications. Entries logged by an admin for someone else are attributed to that member but record who logged them (see `created_by_id`).
- **M3-D2 — Entries are time slots, links are optional.** A `time_entry` is `startedAt → endedAt` + description. It *may* link to a project and/or a card the user can access, but never requires one (Jibble parity: description-only entries are the norm).
- **M3-D3 — Week calendar built in-house** (per D7, no new dependencies): vertical day-column grid, drag-to-create, drag-to-move/resize, 15-minute snapping.
- **M3-D4 — Export = CSV + printable summary; import = Jibble CSV.** No direct invoice generation in V1; the CSV feeds their invoice template, the printable view covers PDF via the browser. Migration uses Jibble's own timesheet CSV export (upload + column mapping) rather than the Jibble API — one-time, per-user, no OAuth plumbing.
- **M3-D5 — The existing card `Timer` stays independent.** No automatic bridging in V1; a "add timer session to my timesheet" action is a possible V2 note, nothing more.

### 15.1 Data model

Migration `create_time_entries`:

```js
// table: time_entry
id (next_id PK),
user_id NOT NULL,
project_id NULL,            // optional link
card_id NULL,               // optional link (implies project consistency; validate server-side)
started_at timestamp NOT NULL,
ended_at timestamp NOT NULL,
description text,
imported_from text NULL,    // 'jibble' when migrated; used for dedupe/idempotent re-import
created_by_id NULL,         // ≠ user_id when an admin logged this on the member's behalf
updated_by_id NULL,
created_at, updated_at
index(['user_id', 'started_at'])
```

Rules enforced in helpers: `endedAt > startedAt`; entries for the same user must not overlap (query for range intersection on create/update; reject with a dedicated exit → 409); if `cardId` is set, derive/validate `projectId` from the card's board; linked project/card must be one the user can access (project member or board member — reuse `projects/get-membership-context` from §3.2).

### 15.2 API

```
GET    /api/time-entries?from&to&userId    → index (range required; userId admin-only, defaults to current user)
POST   /api/time-entries                   → create (body may carry userId — admin-only — to log on a member's behalf)
PATCH  /api/time-entries/:id               → update (owner or admin)
DELETE /api/time-entries/:id               → delete (owner or admin)
POST   /api/time-entries/import            → Jibble CSV upload into the uploader's own timesheet (multipart, skipper — mirror attachments/create)
GET    /api/time-entries/export?from&to&format=csv&userId → CSV download (userId admin-only; mirror the boards/export → /exports/:id/:filename download pattern)
```

Scoping rule, applied identically in every controller: `targetUserId = (inputs.userId && currentUser.isAdmin) ? inputs.userId : currentUser.id`; a non-admin supplying a `userId` other than their own gets a forbidden response. On admin-created/edited entries set `createdById`/`updatedById` to the admin. Import stays owner-only (no importing into someone else's timesheet).

Sockets: a `timesheet:<userId>` room, joined when a timesheet page is opened (join authorized for the owner or an admin — enforce in the subscribe path). All `timeEntryCreate|Update|Delete` events for that user's entries broadcast there, giving both the owner's other devices and any admin viewing that timesheet live updates. Full vertical slice per §13 (`TimeEntry` ORM model, sagas, selectors, etc.).

### 15.3 UI — `/timesheet` (account-level)

Routing: `Paths.TIMESHEET = /timesheet`, rendered by `Static.jsx` exactly like `Paths.NOTIFICATIONS` (inside `SidebarContainer`). Access points: a clock icon button in the `Header` (next to notifications) and an entry in the user menu (`UserPopup`).

`client/src/components/Timesheet/`:

- **Week grid:** 7 day columns (Mon–Sun, locale-aware), vertical hour axis (default visible window 06:00–20:00, scrollable to full 24h), 15-min row granularity, "today" column highlighted. Current-time line in today's column.
- **Create:** mouse-down + drag on empty space draws a slot; on release, a popup (existing `Popup` machinery) opens anchored to the slot: description `TextArea` (autofocused — description-first, Jibble style), the project/ticket picker (below), editable start/end time fields, Save / Cancel. `Ctrl+Enter` saves.
- **Project/ticket picker (build exactly this, not two dropdowns):** a single unified type-ahead. Collapsed state is a subtle "+ Link project or ticket" affordance; opening it shows one search input over two zero-typing sections: *Your projects* (member projects, color dot + name) and *Assigned to you* (cards where the user has a `CardMembership`, ordered by recent activity, subtitle "Project · Board"). Typing filters both sections simultaneously (*Matching tickets* rows show project · board context; substring highlight; `Enter` picks the top result; `Esc` closes). Picking a **ticket directly auto-derives the project** — one search + one click links both. Picking a **project first** shows a project chip and narrows the list to that project's cards, grouped *Assigned to you* / *More tickets* with board-name subtitles. Selection renders as removable chips: the ticket chip's × removes only the ticket (project link stays); the project chip's × clears both. All data comes from the ORM/selectors already in the store (member projects; CardSearch-style card filtering) — no new endpoints.
- **Edit:** drag body to move (within a day or across days), drag top/bottom edges to resize, click opens the same popup. Delete inside the popup (with the existing confirm-step pattern). All snapping to 15 min; optimistic updates; a server 409 (overlap) rolls back with a toast-style message.
- **Entry rendering:** slot shows description (truncated), time range, and — when linked — a small project color chip / card name line. Entries linked to a project use that project's background color as a muted left accent bar; unlinked entries use the neutral accent.
- **Totals:** per-day total in each column footer; week total + billable-days summary in the header row. Header also has: prev/next week arrows, "Today", a date picker, a **"Copy previous week"** action (duplicates last week's entries into empty days — Jibble parity), and the Export + Import buttons.
- **Empty state:** "Drag anywhere to log your first time slot."
- **Admin member switcher:** for admins only, a user `Dropdown` in the timesheet header ("Viewing: Me ▾" → member list with avatars). Selecting a member loads their week (same grid, same interactions — admins can create/move/resize/delete entries on it); a subtle banner line notes whose timesheet is shown. Entries the admin logs there are attributed to that member, and the edit popup shows "Logged by {admin name}" metadata when `createdById ≠ userId`. Non-admins never see the switcher.

### 15.4 Export (invoice feed)

Export popup: date-range picker (presets: this week, last week, this month, last month, custom), optional project filter, group-by (`day` | `project` | `none`). Admins additionally get a member scope selector (current member as shown in the switcher, or **all members** — which adds a `member` column and per-member subtotals, for consolidated invoicing). Two outputs:

- **CSV** — columns: `date, start, end, duration_hours (decimal), description, project, card, imported_from`; grouped subtotal rows optional; final total row. Duration as decimal hours (e.g. `1.75`) so invoice spreadsheets can sum directly.
- **Printable summary** — an in-app print-optimized view (`@media print` stylesheet, light background regardless of theme): date-grouped table with daily subtotals and grand total; user prints to PDF from the browser. This is the "send to LRS" artifact until a real invoice generator is warranted.

Stretch (only if trivial): optional hourly rate stored in `UserPrefs` → computed amount column in both outputs. Do not build rate/currency management beyond a single number.

### 15.5 Jibble import (one-time migration)

- Timesheet header → "Import" → upload popup accepting Jibble's **timesheet CSV export** (instruct the user in the popup: Jibble → Reports/Timesheets → export CSV; XLSX must be re-saved as CSV — do not add an xlsx parser dependency).
- Server parses the CSV and returns a **preview** (first ~10 rows + detected columns); client shows a column-mapping step (Date, Start, End, Duration, Activity/Project → project name hint, Note → description) with sensible auto-detection of Jibble's default headers; user confirms; server creates entries.
- Idempotency/dedupe: skip rows matching an existing entry on `(user_id, started_at, ended_at)`; mark created rows `imported_from: 'jibble'`. Report `created / skipped / failed` counts back to the popup.
- **Time zones:** Jibble exports local times; parse in the user's browser-reported IANA zone (send it with the import request) — do not assume server TZ. Overlap validation applies; overlapping imports are reported as failures, not silently dropped.
- Import is strictly into the uploading user's own timesheet. Jibble's project/activity names are stored as plain-text prefix in the description (`[Activity] note`) unless they exactly match one of the user's project names, in which case the entry links to it.

### 15.6 V2 candidates (explicitly not in V1)

- **Activity presets (prefills):** an admin-managed, instance-wide list of common non-ticket activities ("Meeting", "Admin", "Support", …) that users can tap to pre-fill the description in the Log time popup (shown as small chips above the description field; tapping inserts the text, which stays freely editable). Admin manages the list in Instance settings (`/settings/instance`) — add/rename/remove/reorder. Storage: a json array on the existing `Core` settings record (no new table; follow how other instance settings fields are stored and broadcast). Entries keep storing plain description text — no schema change, no new entity; deleting a preset never touches existing entries.
- **Card timer bridge:** "add timer session to my timesheet" action converting a card `Timer` run into a `time_entry` (see M3-D5).

### 16.2 My Work dashboard

Account-level page (route + `Static.jsx` branch like `/timesheet`): cards assigned to me across all projects bucketed *Overdue / Due soon / No date*, recent notifications, and this week's logged hours (M3 data). Mostly reselect selectors over ORM data already loaded at bootstrap plus the existing `cards-summary` endpoints — minimal new server surface. Could become the default landing page (user pref).

### 16.3 Client share links (read-only external views)

Tokenized, unauthenticated, read-only views of a board or a project gantt — lets the LRS client watch progress without membership.
- `share_link` table: `id, target_type ('board'|'gantt'), target_id, token (random, unique), expires_at NULL, created_by_id, timestamps`. Managed (create/revoke/copy) from board/project settings by managers+.
- Unauthenticated route `GET /share/:token` renders a stripped view: no edit affordances, no popups, no member emails (names/avatars only), no navigation outside the shared target. Server validates token + expiry and returns a read-only payload; never reuse authenticated endpoints for this.
- Philosophy matches M2's PenPot share-link viewer: static, revocable, scoped.

### 16.4 Card estimates + actual vs estimate

Nullable `estimate_minutes` on `card` (migration + include everywhere like `dueDate`). Card modal gets an estimate field; card modal, list view, and gantt tooltip show **logged** (sum of linked M3 time entries) vs estimate with an over-budget highlight (existing warning color). Requires M3 shipped; the rollup is a selector joining `TimeEntry` by `cardId` (server aggregate endpoint only if the client-side sum proves insufficient).

### 16.5 Admin team hours report

Admin page (settings area, next to Members): aggregate time entries by member × project over a date range; totals, per-member and per-project subtotals; CSV export with `member` column (shares the M3 export code path with `userId=all`). Powered entirely by M3's admin read access — no new permissions concept.

### 16.6 iCal feed / calendar view

Per-user tokenized read-only iCal URL (`GET /calendars/:token.ics`) containing due dates of assigned cards and planner assignments; token generated/revoked in Preferences. Standard `text/calendar` output, no dependency needed (hand-rolled VEVENT serialization is fine). An in-app month calendar view is a separate, later consideration — the feed is the cheap 90%.

### 16.7 Admin audit log

Append-only `audit_event` table: `id, actor_id, action (text enum), target_type, target_id, meta json, created_at` — written from helpers for admin-relevant events: user create/delete/role change, project/board create/delete, membership changes (project + board), instance settings changes, and admin-on-behalf timesheet edits (M3). Admin-only settings page with a filterable table (actor, action, date range) using `Utils/Table`. No update/delete API for events — append-only by construction. Do **not** log ordinary card activity here; that's what `Action` records are for.

## 17. Known traps

- **CRLF:** `.gitattributes` exists and eslint is clean today — keep it that way; run `git diff --check` after batch edits.
- **Waterline quirks:** `columnName` snake_case on every multi-word attribute; enums as module-level consts exported alongside `attributes`; use `.intercept('E_UNIQUE', ...)` for unique violations (see card-links helper).
- **Dates over the wire are strings**; deserialize in `client/src/api/transformers` exactly like `dueDate`.
- **Socket payload discipline:** broadcast the affected item(s) only; heavy fields (wiki content) excluded from list-level events.
- **Don't regress attachments:** Documents copy the file pipeline; any shared-helper extraction must keep `attachments/*` behavior byte-identical.
- **react-beautiful-dnd** is strict about nested droppables — the wiki tree uses one droppable per parent with distinct `type`s (see `DroppableTypes.js`).
